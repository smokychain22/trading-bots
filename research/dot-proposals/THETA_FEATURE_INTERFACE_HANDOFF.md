# Source-pinned feature semantics and actual Dot consumer read-set

Source: `d0b479f3dfd0a6d9a1e79a699308cab09ed9f1ba`, frozen current V4 branch verified earlier in this audit. Read-only extension; no new synthetic cases, proposals, engine, router, schema or production changes.

## Conclusion

Useful, typed upstream feature evidence exists. The current Dot canonical proposal path does **not automatically convert or verify those producer values into its numerical research-rule scalars**. The HTTP caller supplies `features` separately from sealed T0 and supplies `sourceEvidenceIds`; canonical proposal consumer forwards them to `qualifyDotProposal`, which validates labels, times and equality bindings, then gates the entire snapshot. It neither derives candidate features nor verifies the scalar equals a particular field of a source payload. This is an adapter/provenance gap for research reuse, not a finding that upstream producers have no units or integrity controls.

Do not encode cost-to-credit or VRP admission by renaming a scalar IV/LIQUIDITY. The existing source supports truthful offline candidate diagnostics using canonical economics, and existing typed soft-feature/VRP research functions. A meaningful new admission proposal requires an explicit valid mapping with scope, units, method and allowed decision role. Source-provider qualification alone is not empirical qualification.

## Data flow and integrity, without overstating it

1. Actual cycle builds technicalFeatureState with method/unit labels, fields and source timing (`theta-shadow-cycle.ts:1057–1090`). It inserts it into FusionSnapshot.regimeState.technicalFeatures (`:633–635`) and creates technical-feature provenance content hash (`:709–715`). `fusion-snapshot.ts` validates JSON safety/version/provenance records, computes whole snapshot hash and freezes it. Thus units/methods can be source-hashed upstream, not merely prose.
2. Optionomics feature snapshot retains underlying, contract identities, responseHash, observed/available/retrieved times and field states (`optionomics-feature-engine.ts:60–97`). Contract IV normalization does not by itself verify external documented units; its acceptance rule is explicit and conservative rather than a scale guess.
3. T0 replay bundle seals normalized contracts, routing, opening-cost policy and optionomicsContext (JSON) with input-contract and whole-bundle hashes; replay verifies these and deterministic frontier result (`t0-replay-bundle.ts:122–150,171–177,256–285`). A hash establishes reproducibility of supplied content, not factual authenticity or licensing.
4. Dot HTTP `/v1/research/canonical` parses separate unknown `features` and caller `sourceEvidenceIds` (`lab/http.ts:83–87`). `evaluateDotCanonicalProposal` verifies sealed T0, snapshot/routing and account inventory for A/C, then forwards separate feature records (`lab/canonical-proposal-consumer.ts:19–31`). It does not join to technicalFeatureState or source payload content.
5. `qualifyDotProposal` exact evidence read-set: feature/value/evidenceId/snapshotId/observedAt/availableAt/validUntil/qualification. It requires unique feature labels, finite non-null value, QUALIFIED, correct snapshot, evidence-ID membership, observed≤available≤decision<validUntil, matching decision/routing time. Each rule is a GTE/LTE/BETWEEN comparison. Any unavailable/rejected rule blocks the full snapshot (`lab/proposal-consumer.ts:12–56`).
6. Receipt inputHash commits the supplied bundle/evidence/binding together after evaluation (`canonical-proposal-consumer.ts:62–64`). It does not prove the scalar was correctly derived from a preexisting sealed producer record. Named evidence ID membership is a necessary identity check, not cryptographic payload equality.

This conclusion rests on inspected entrypoint and call chain, not solely missing fields in a schema. An external caller could manually provide a correct adapter; no such deployed or executed adapter is established by this read-only audit. Do not claim a universal repository-wide absence or deployed defect.

## Consumed versus unconsumed fields

Consumed by qualification: exact canonical baseline/strategy identity and validation; unchanged candidateLatticeVersion, featureSetVersion, entryModelVersion, ownershipModelVersion, managementPolicyVersion, softFeatureFamilies, allowedActions, optionType, deltaResearchBuckets; narrowed DTE window; rule list and the precise evidence read-set above.

Consumed by canonical candidate retention: branch, unchanged recovery lattice, DTE bounds, sealed canonical candidates. Ranks/blockers/quantities/economics remain untouched. No new selection authority.

Not consumed for feature arithmetic: hypothesis text, unit/method explanations in that text, experimentId naming, feature provider/payloadHash/first-seen/contract identity from richer upstream structures unless a verified adapter supplies and preserves those externally. Those additional keys cannot simply be inserted into strict Dot featureSchema. No automatic IV minus RV, ratio, covariance or per-candidate expression exists here.

Entry consumers explicitly report plannedHoldingDays and profitTakingChallengers as unconsumed experiment fields. The separate exit comparator uses plannedHoldingDays as maxHoldingMinutes and reports all policy trials; it does not turn an entry proposal into a management policy. `runDotBaselineReplay` additionally declares proposalRulesApplied=false and CHALLENGER_RULE_CONSUMER_NOT_CONNECTED; do not cite it as rule execution.

## Precise safe reuse paths

### Cost-to-credit now, without new engine/schema

Use a sealed T0 bundle and existing canonical replay to obtain all candidate economics, preserving candidate IDs, rejection reasons, ranks and quantity. Attach an offline research annotation per candidate using modeledOpeningCosts.total/grossPremium with UNKNOWN preserved. Distinguish opening-only ratio from total round-trip costs; for round-trip use actual qualified close costs and known fee model, with censoring. Compare after-cost outcomes over the same opportunity set. This is a diagnostic/research design, not a validator-consumed candidate gate. No attempt should map this ratio to LIQUIDITY or EXECUTION_QUALITY without an explicit, approved semantic contract.

### IV/RV and physical-variance research now

Reuse typed source contract/ATM evidence and PIT materializer, explicitly recording the chosen IV source, selected expiry, RV window, annualization and availability. The existing VRP function can produce honestly labeled arithmetic diagnostics. `computeShadowFeatureContribution` offers existing research rank comparison using typed soft evidence and disclosed BOOTSTRAP_NON_EMPIRICAL weightVRP20=1, ATM_IV=RV20=0; it does not establish a profitable ranker or live weight. It accepts CURRENT_ONLY as well as bounded PIT_SAFE, so historical/OOS work must independently require PIT_SAFE rather than assuming every returned score is historical-safe.

For new physical variance forecast versus ACT365 horizon, source technical RV sqrt252 is a comparator, not a drop-in target. Keep forecasting/ATM-IV-squared proxy in a versioned research design, not Dot scalar IV or certified EV.

### Possible future Q scalar gate

Only after economic review, a research-only snapshot-level gate could truthfully use one explicitly derived, qualified underlying metric (e.g., existing return5d or normalized trend20) together with DTE narrowing. It must retain an independently reviewable producer/field/unit/method/version/hash mapping and fixed decision role; missing semantics cannot be repaired by placing an arbitrary number in the allowed enum. No proposal was generated or validated in this source-only extension.
