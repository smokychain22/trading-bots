# THETA disaster recovery

## Permanent portability contract

Every new format-v2 backup includes `database-structure.json`, `global-state.json`, `all-table-row-counts.json`, `critical-data-digests.json`, `sequence-state.json`, and `external-assets-inventory.json`. The structure file is a deterministic PostgreSQL catalog fingerprint. Function bodies, policy expressions, defaults, trigger definitions, index definitions, and constraint definitions are represented by hashes in that JSON, not copied as readable text. The complete definitions are in `schema.sql` and the custom `pg_dump -Fc` archive. The fingerprint covers schemas, base and partitioned tables, partition parents/bounds, columns and identity/generated/default metadata, PK/FK/unique/check/exclusion constraints, partial/expression indexes, sequence definitions and ownership, views and materialized views, functions/procedures, user triggers, rules, enum/domain/composite/range types, domain constraints, RLS flags/policies, extensions/versions, large-object count, and migration history.

`global-state.json` records sanitized role names and attributes, database/schema/object/routine owners and grants, default privileges, database/role setting names, tablespaces, and extension classification. Provider-owned roles and tablespaces are `PROVIDER_MANAGED_RECREATE`. Any role password and setting value is `SECRET_RESTORE_SEPARATELY`. The restore uses `--no-owner --no-acl` so a new provider can accept the archive without Aiven roles. The new provider must recreate any required application-specific roles/grants separately. The present Aiven source has no application-specific roles, object ACLs, or default-privilege entries beyond provider/public defaults. Do not claim ownership or provider-managed role parity across providers.

The restore now computes the same structure fingerprint on the target, exact row counts for every application table and materialized view, sequence state, and deterministic row-content digests for critical THETA tables. It emits `STRUCTURE_PARITY`, `DATA_ROWCOUNT_PARITY`, and `CRITICAL_DATA_VERIFICATION`. A successful `pg_restore` alone never promotes a format-v2 backup. A scheduled run performs an isolated PostgreSQL 18 local restore before updating `latest/current.json`. The previous verified pointer is kept in `latest/previous.json` and protected from daily retention pruning. The original seven daily, four weekly, and three monthly retention buckets remain in place.

The critical digest method is recorded in each manifest. `ORDER_INDEPENDENT_DUAL_SUM_V1` streams per-row MD5 halves into two exact numeric sums plus a row count, then hashes that summary. It does not require a database temporary sort file. Older format-v2 archives without this marker retain `SORTED_ROW_MD5_V1` for restore compatibility. Neither table digest replaces the custom archive's SHA-256 checksum or the complete PostgreSQL restore test. On 2026-09-22 the sorted method failed specifically on `trade.candidate_point_in_time_evidence` with PostgreSQL `No space left on device` for a temporary file. The streaming method passed a protected read of that table without writing to Aiven.

All backup and restore PostgreSQL client sessions set `PGTZ=UTC` and restore the caller's prior environment afterward. This is required for byte-stable JSON row digests across Aiven's GMT default and a local restore cluster configured for another timezone. A real Aiven-to-local comparison verified all 13 critical-table digests after this correction. The first production format-v2 run correctly refused promotion when its structure and row counts matched but its digests differed because of timezone rendering.

`logs/database-size-trend.jsonl` records each verified source database size and archive size. If an authenticated Aiven disk capacity is supplied as the non-secret `AIVEN_DISK_CAPACITY_BYTES` environment variable, it also reports the database-to-disk fraction and warns at 70%. This ratio excludes WAL and provider overhead, so it is an early warning, not a complete disk-free metric. Without a verified capacity, the trend explicitly says `CAPACITY_UNVERIFIED` and cannot claim an Aiven quota percentage. Capture the actual free/used disk metric from Aiven before making capacity decisions.

Production migrations on the local canonical Aiven connection must use `tools/windows/dr/Invoke-ThetaProductionMigration.ps1`. It requires a verified, test-restored backup before migration, runs schema/invariant verification afterward, then takes and test-restores a post-migration backup. A newly completed capture may be reused with `-UseFreshVerifiedLatest` only when its manifest says Aiven, its backup ID and archive hash match the verified latest pointer, its source Git SHA matches the current checkout, its migration head matches the live database, restore parity passed, and its age is within the explicit six-hour default. The ordinary `tools/database-migrate.mjs` refuses Aiven unless called inside this checkpoint workflow. The legacy remote bootstrap migration operation is disabled once Aiven is the production runtime authority. If a migration or post-check fails, the pre-migration backup remains preserved and no automatic destructive rollback is attempted. Do not run production migrations while Aiven is read-only.

Every backup process also acquires one machine-wide named mutex. A scheduled run that overlaps a manual or migration-checkpoint capture exits with `BACKUP_ALREADY_RUNNING` instead of starting a second full Aiven dump. Production captures hold one exported, repeatable-read PostgreSQL snapshot for the custom archive, schema SQL, structure/global inventories, all-table counts, sequence state, critical digests, and human-readable critical-table exports. The snapshot holder stays alive with bounded read-only keepalives until database capture completes. This prevents normal worker writes during a long dump from creating a false restore-parity failure.

## Files and schedule

Each verified run is published at `daily/<UTC timestamp>-<suffix>/` and contains `database.backup` (`pg_dump -Fc`), `schema.sql`, `database-inventory.json`, `extensions.json`, critical-table JSON, allowlisted external assets, `source-code.bundle`, `backup-manifest.json`, `SHA256SUMS.txt`, and `verification.json`. `latest/current.json` points to a verified daily run. Staging folders are never treated as valid backups and are removed on failure. A new failed run never rewrites a previous verified archive.

After each successful run, one independently copied and checksum-verified archive is kept per ISO week and month. Retention keeps seven daily, four weekly, and three monthly directory copies. Pruning runs only after a newly verified daily backup exists. It never targets the backup root or a computed path outside the selected bucket. The schedule is 02:15 local time, with `StartWhenAvailable` and no overlapping instances. The task runs under the current logged-in Windows user so user-bound DPAPI can decrypt the source URI. It may run on battery, but the script refuses to start a production backup if the laptop is discharging below 40%. A sleeping, powered-off, logged-out, or disconnected laptop cannot guarantee a daily run. Monitor the task and logs.

## Restore to another PostgreSQL provider

1. Keep THETA new-risk execution locked. Stop the worker only when an actual cutover is authorized and coordinated. Record the current Alpaca Paper account, orders, fills, positions, and broker activities separately. A database backup cannot replace broker truth.
2. Select the latest `VERIFIED` archive, run the verification script, and provision a new empty PostgreSQL 18-or-newer database with required extensions available. The restore script refuses a target containing user tables, views, sequences, or foreign tables. It never uses `--clean`, `--if-exists`, or `--create` against a running database.
3. Supply the new target PostgreSQL URI to `Restore-Theta.ps1` through the `THETA_RESTORE_TARGET_URL` process environment or its `-TargetUrl` parameter. Environment use avoids a URL in the process command line. Restore external assets to a new, empty target directory. For a format-v2 backup, the script compares the canonical structure fingerprint, all application table row counts, sequence state, critical-table content digests, extensions, and migration head. It writes a restore receipt under `restore-tests/`.
4. Restore secret values separately through the new provider and deployment secret manager. Preserve the existing broker-credential encryption key if the encrypted database credentials must remain usable. Never commit or copy secret values into the backup repository.
5. Update `DATABASE_RUNTIME_AUTHORITY`, `AIVEN_DATABASE_URL`/`DATABASE_URL` routing deliberately for the new provider, redeploy the website and worker from the pinned Git source, and verify the app, migrations, customer sign-in, provider reads, and Alpaca reconciliation. Keep Paper entry locked until idempotency, open orders, fills, positions, leases, and account roles agree. Followers and live money stay disabled.

The script accepts a different provider, but the current production runtime code expects `DATABASE_RUNTIME_AUTHORITY=AIVEN` and `AIVEN_DATABASE_URL`. A migration to another provider therefore needs a tested environment-routing change and redeploy. Restoring bytes alone does not cut over the app.

## Limits and additional resilience

A backup on the same laptop and `C:` drive removes Aiven as the only copy, but it does not survive loss or corruption of that laptop. Keep at least one encrypted offline or offsite copy of the verified backup root, with its decryption/recovery procedure tested separately. The backup script does not claim BitLocker is active. Local asset copies may lag a file being written concurrently; the included research exports and evidence are designed as immutable content-addressed artifacts, and all copied bytes are checksummed after copying. PostgreSQL archive data and every database-side parity inventory share one exported repeatable-read snapshot. Filesystem assets are copied afterward and have separate checksums rather than transactional database semantics.

Daily snapshots have a recovery-point gap of up to one day, plus any missed runs. New rows written after the latest verified backup still have Aiven as their only physical database copy. Meeting a literal zero-data-loss requirement needs an independent continuous replica or verified WAL archiving with recovery replay. Neither is configured here. Treat the local backup as tested portable recovery, not as synchronous redundancy. The backup is also not encrypted as an archive, so protect the Windows volume and any future removable or offsite copy before it leaves this machine.
